# 增量 Prompt / Incremental Prompt

## ChatAgent 专项补充

把原始需求拆成产品目标、身份/权限、任务状态、工具副作用、产物/交付和验收条件；不要只记录“让模型更聪明”。涉及 ChatAgent 时保留“内网原生聊天 vs 外部 IM”“开发 Harness vs 产品 Hermes”“Mock vs 真实模型/网关”的决策。

每条记录增加：受影响 package/符号、前置权限、数据分类、是否会外发、幂等/取消语义、测试 profile、未验证边界。脱敏 Prompt 不得保存 key、token、文件原文、收件人私人载荷或 reasoning_content。

语义去重不能只按标题；判断任务目标、授权范围、外发目标和验收是否改变。目标或授权改变必须新记录并关联旧记录；只调整措辞或补充测试则更新使用元数据。完成后写入真实命令、状态、产物、失败和下一 Prompt；不得把计划写成已完成。

用于已有项目的二次修改、调整、Bug 修复或后续请求。未发生实质变化的指令不要重复创建记录。

## 工作流 / Workflow

1. 检查项目环境，确认是否已有可用的 Embedding 模型和向量数据库配置。检查现有配置、依赖、Schema、索引和已记录命令，不要为了满足本技能而安装新服务。
2. 在不改变用户意图的前提下规范化原始指令。保留用户措辞，但脱敏秘密，并记录时间、项目或仓库、变更请求、约束、影响范围和验收标准。
3. 如果已有高质量 Embedding 与向量数据库路径，使用项目现有接口保存原始指令及其向量，并保存足以按项目、日期、受影响组件和需求检索的元数据。不要保存凭据或其他秘密。
4. 如果该路径不存在、不可用，或用户明确拒绝，则将脱敏后的原始 Prompt 以 Markdown 写入项目 `Prompt/` 目录。使用 [references/prompt-record.md](references/prompt-record.md)，并把项目 `Prompt/` 目录明确传给辅助脚本。
5. 保存前按语义或规范化内容去重。实质变化的请求创建新记录并关联旧记录；未变化的重复请求只更新使用元数据。
6. 将已保存 Prompt 作为当前计划、需求、实现和验收测试的输入。如果它与项目核心文档冲突，应提出决策，不要静默改变方向。
7. 实现完成后，在记录或关联变更文档中补充结果、变更文件、测试、未解决事项和后续 Prompt。

## 存储边界 / Storage Boundaries

- 优先使用项目已有 API 和 Schema，不要新建向量格式。
- 即使使用向量，也保留人类可读的 Prompt 文本。
- 不要持久化秘密、访问令牌、密码或私有载荷。
- 向量存储失败时保留 Markdown 记录，并报告回退。
- 创建新记录前，对比现有记录或辅助脚本的 Prompt 索引；未变化的重复请求应复用原记录。
- Prompt 记录放在项目内，不要放进全局 Agent 配置。
