# 项目测试 / Project Testing

## ChatAgent 专项测试门

除普通功能测试外，所有涉及 AI 账号、消息、工具、文件或外发的变更都要覆盖：匿名/跨用户拒绝、Webhook 签名与重放、同会话顺序、工具参数零副作用、任务异常、取消竞态、崩溃恢复、产物归属、审批载荷 hash、幂等重试和交付 unknown。

将验证分为五档并单独报告：Mock 离线、内网模型协议、上游 Hermes 集成、真实 IM 网关、真实收件人交付。低档通过不能替代高档；缺少密钥、平台账号或收件人时标记 BLOCKED，不假设通过。

任务测试必须断言结构化终态而不是 UI 文案；外发测试必须断言网关调用次数、业务回执和审计记录；文件测试必须断言 task/run/owner 绑定及下载授权。记录模型 id、协议、固定版本、日期和脱敏错误，不记录 token、完整文件或推理原文。

开发阶段完成、Bug 修复需要验证或项目需要最终验收时使用。真实环境可运行时，不要用代码审查替代可执行测试。

## 测试工作流 / Test Workflow

1. 阅读需求、任务、架构、环境记录和变更文件，确定受影响的行为边界和耦合边界。
2. 使用 [references/test-plan.md](references/test-plan.md) 定义阶段门，包括进入条件、测试用例、预期结果、必需凭据或配置，以及退出条件。
3. 根据变更风险分层验证：
   - 静态检查、类型检查和 Lint
   - 聚焦的单元或组件测试
   - 跨变更边界的集成和耦合测试
   - 面向用户流程的端到端或浏览器测试
   - 构建、打包和启动验证
   - 在风险需要时执行安全和性能检查
4. 在实际可用环境中运行测试。需要密码、令牌、私有端点、服务、设备或外部数据时，在测试前向用户索取，并且只记录安全元数据，不记录秘密本身。
5. 在项目 Bug 记录中记录失败、复现步骤、根因、修复和重测结果，不要隐藏可能影响行为的警告。
6. 最终验收时，对照需求和文档，执行所有支持的用户流程，检查 UI 和浏览器行为，并输出带剩余风险的验收报告。

## 证据规则 / Evidence Rules

- 区分通过、失败、阻塞、跳过和不适用。
- 包含命令、日期、环境、结果以及相关产物或日志路径。
- 必要外部条件不可用时，测试状态应为阻塞，不能记为通过。
- 未解释的控制台错误、影响行为的构建警告、随机失败测试和未测试的集成边界都应作为开放风险。
- 不要把测试凭据和敏感值写入提交的文档。

## 完成标准 / Completion Criteria

- 变更行为和受影响接口具有可执行覆盖，或有书面理由说明为何不覆盖。
- 阶段测试和最终测试都有证据。
- Bug 与验证结果相互关联。
- 剩余缺口和风险明确。
