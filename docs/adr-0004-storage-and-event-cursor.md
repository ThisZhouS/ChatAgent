# ADR-0004：本地存储与事件游标

状态：已接受（2026-09-18）。相关：ADR-0003（关窗常驻的生命周期）、`docs/product-decomposition-gap-matrix-2026-09-17.md`。

## 背景

服务端目前的持久化是**一组 JSON 文件**（`data/*.json`），每个 store 用「内存 Map + 合并写入 + write→fsync→rename」的模式，配合单进程单写者（`docs/security-checklist.md` 已声明只允许单进程）。消息经 SSE 推送，客户端重连时按 `Last-Event-ID` / `?since=` 回放**内存里的有界环形缓冲**（500 条）。

产品功能树要求「消息的分发与同步」「消息的存储（本地）」。本轮把「继续用 JSON 还是迁移数据库」以及「事件游标怎么保证不丢」写成决策，并实施其中确定的一步。

## 决策一：存储暂时保持 JSON 文件，但设定明确的迁移触发条件

**理由（支持现状）**

- 部署目标是**内网单机**：一个组织、一台服务器、一批员工。JSON 文件没有外部依赖，备份就是复制目录，出事时能用编辑器看懂，符合「可维护性优先于吞吐」。
- 写入路径已经具备三个关键性质：**原子替换**（写临时文件再 rename）、**fsync 后返回**（不声称磁盘上没有的结果）、**单写者锁**（多实例启动会被拒）。这些性质在 SQLite 上同样需要，但换成 SQLite 要重新证明一遍。
- 现有测试（403 例）大量依赖「进程内可枚举、可直接断言」的存储行为，迁移成本不在存储本身，而在这些断言的迁移。

**已知代价（不粉饰）**

1. **没有跨 store 事务**：消息、会话、任务、回执分属不同文件，一次逻辑操作可能跨两三个文件（例如「发消息 + 入队投喂」）。目前靠**顺序 + 幂等键**兜底，而不是靠事务。
2. **全量重写随历史增长**：单文件保存整个消息表，写放大与文件大小线性增长。消息 store 已有分页与 150ms 合并写，但没有按会话分片。
3. **没有查询能力**：检索是进程内子串匹配（`stores.ts`），搜全部历史要全量载入内存。

**迁移触发条件（先写清楚，避免“以后再说”）**

出现下列任一情况即启动 SQLite 迁移评估（**不是**立即迁移）：

- 单组织消息总量 > 200k 条，或 `messages.json` > 100 MB；或
- 任一 store 的单次写入 p95 > 200 ms（合并写之后仍如此）；或
- 需要**跨实体的原子操作**（例如「扣减配额 + 写消息」必须同时成功）；或
- 出现多进程/多实例部署需求（当前被单写者锁明确拒绝）。

**迁移路径（保持低成本）**：所有 store 已经是**端口**（构造注入、无全局单例），迁移时在 `apps/server/src/stores.ts` 内替换实现即可；SQLite 选 `better-sqlite3`（原生模块，需验证 Windows 打包与 Electron 侧的 ABI，这一点是本项目选择它而非 Postgres 的原因——后者要求部署方多维护一个服务）。**不做**：现在为了“以后可能”而引入 ORM 或改写全部断言。

## 决策二：事件游标必须能区分「没有新事件」与「我漏了事件」

**问题**：回放缓冲是内存里的，进程重启即清空。客户端拿着一个旧游标重连时，旧实现返回**空列表**——客户端合理地相信「离线期间什么都没发生」，于是永久少了一段消息。这是一个会静默丢内容的缺陷，比报错更难发现。

**做法（本轮已实施）**

- 缓冲记录**最旧序号**；`since(cursor)` 返回 `{ entries, truncated }`，当游标早于仍持有的范围时 `truncated = true`。
- SSE 在回放前先发一条 `event: resync`（`reason: cursor_expired`），然后照常回放仍持有的事件。
- 客户端收到 `resync` 即重新拉取当前会话与会话列表（复用既有的重连补拉逻辑），因此**要么拿到增量，要么明确重载**，不存在第三种「以为自己是新的」。

**为什么不做持久化事件日志**：把事件流落盘等于再实现一遍消息表，而消息表已经是权威来源；游标过期时重新读取权威来源（重载）比维护第二份日志更简单，也不会出现两份历史不一致的问题。若将来需要**跨重启的完整事件回放**（例如审计级订阅），那属于新的需求，届时以「事件表」而不是「日志文件」的形式加入。

## 后果

- 存储：短期内不变，迁移条件可观测（消息量、写入延迟、原子性需求、多实例需求）。
- 事件：断线补差在「缓冲区够用」时给增量，在「不够用」时给明确的重载信号；两条路径都有测试覆盖。
- 未覆盖：跨 store 的原子性仍是「顺序 + 幂等」而不是事务；这是当前架构成熟度下可接受、但已被记录在案的取舍。
