## 运维该盯的计数

- GET /api/agent/status 的 intake.failed > 0：环境在拒收工作（最常见是没配模型凭据、工作目录被锁）。这是试点期最该告警的一个数，不要当成用户问题。
- intake.stalled > 0：队列正在退避重试中，通常自愈；与 failed 同时出现说明环境问题已持续到耗尽预算。
- 重试预算由 CHATAGENT_AGENT_INTAKE_MAX_ATTEMPTS 控制（默认 8 次、约 10 分钟）；调大等于「宁可长时间重试也不要放弃」，调小等于「更快把问题摆到台面上」。

## 线上状态抽查的一次失败（2026-09-21，如实记录）

本轮想用运行中的服务端（http://localhost:8787）直接抽查 /api/agent/status 是否带上新增的 intake 字段（maxAttempts / failed / stalled），**没做成**：带 Temp/owner-token.txt 的请求被服务端以 error 对象拒绝，accounts 与 intake 都取不到。

- 未定因：可能是请求头形式不对（我用的是 Authorization: Bearer，未逐一试其它形式），也可能是该令牌相对当前运行的实例已失效。**两种情况都没验证，所以不下结论。**
- 影响面：这不是产品缺陷的证据；投喂字段的正确性由 HEAD 上的进程内测试与 HTTP 级 agent-intake-wiring.test.ts（断言 maxAttempts: 8、failed/stalled 计数）覆盖，那部分证据不受影响。
- 对后续的意义：**线上抽查要先用 scripts/ 里的成员脚本从当前实例取令牌**，不要假定 Temp/ 里的旧令牌仍可用；抽查失败要当成「未验证」，不是「已通过」。

**已查清（同一轮内）**：问题不在服务端而在凭据。实测三种情况——不带请求头 -> 200、带空 Bearer -> 200、带**无法识别**的令牌（含 Temp/owner-token.txt 里那个）-> 401 authentication required。apps/server/src/auth.ts 写明凭据顺序为「member API token -> native session token -> 开发主体注入（仅 development 模式，loopback 限定）」，所以 development 下无凭据的本地请求会被当成开发主体，而**认不出的凭据是拒绝而不是忽略**（这点是对的）。线上抽查本来就能做，只是不该拿 Temp/ 里的旧令牌。

**顺带拿到的线上证据**：/api/agent/status 实际返回 intake: {"mode":"deferred","deferMs":120000,"contextMessages":20,"pending":0,"submitted":30,"cancelled":0,"failed":0,"stalled":0,"maxAttempts":8} —— 第 18 轮新增的 failed/stalled/maxAttempts 在运行实例上确实存在，队列健康，且服务端确实跑在产品默认的 deferred 模式（此前只是我的说法，现在有实测）。

## 线上实测汇总（2026-09-21，开发实例 http://localhost:8787）

这些都是**运行态**实测，用来证明「行为与文档一致」，**不等于 Gate 7A.3**（那需要真实 Hermes 运行时与模型凭据）。方法上：无凭据的 loopback 请求在 development 模式下会拿到开发主体身份，因此 curl 即可探测；**探测脚本必须打印原始响应**，只打印派生布尔值会把错误形状读成通过（本轮踩过一次）。

| 控制点 | 实测 | 结论 |
| --- | --- | --- |
| 文件签名边界 | 纯文本伪装 .docx → **415** `unrecognised_signature`，审计写 `upload.rejected` | 运行态生效，且失败发生在落盘前 |
| 成员资格（发送） | 向非参与者会话发送 → **403** `not_a_participant`，零落库 | 硬门，不靠界面隐藏 |
| 发送幂等 | 同一 `clientMsgId` 连发两次 → 同一消息 id，会话内仅 1 条 | 重放不产生第二条消息 |
| 开发主体注入 / 凭据失败 | 无凭据 → 200；无法识别凭据 → **401** `authentication required` | 认不出的凭据是拒绝而非忽略 |
| 投喂队列状态面 | `/api/agent/status` → `deferred / pending / submitted / failed / stalled / maxAttempts: 8` | 第 18 轮新增字段在运行实例上存在，队列健康 |
| 事件游标（P2-7） | 无游标 → 仅 `: connected`；`Last-Event-ID: 1` → 从 `id: 2` 起重放事件 | 缓冲期内重放、不是静默空流 |

交叉印证：重放出来的那条 `agent_intake` 正是幂等实测那条消息（`189e3468-…`），`state: pending`、`dueAt` 比发送时间晚 120 秒——**投喂闸门（P0-1）与事件游标（P2-7）在同一个实例上互相印证**。
